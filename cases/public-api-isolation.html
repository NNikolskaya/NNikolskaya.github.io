03 / Architecture · Failure isolation

Isolating a public API from a legacy system

An independent contract required a public API for the latest available data from a legacy platform. The source application already had an authenticated API, but changing it for anonymous internet traffic would have increased risk to the core system.

Architecture · Failure isolation

Context

The new endpoint had to be public. The legacy application needed to remain isolated from unpredictable external request volume and from failures at the public edge.

The constraint

The public service could be overloaded or compromised. It therefore needed only the data intended for publication, without direct access to core services or the credentials used for internal synchronization.

What I did

  1. Separated the internal synchronization process from the internet-facing API.
  2. Stored a controlled copy of public data in a dedicated store and served external requests from that copy.
  3. Made the public layer reproducible so recovery did not depend on repairing a unique server in place.

Outcome

External traffic no longer translated into proportional load on the legacy platform. The public API could continue serving the last synchronized data between updates, and a failure at the public edge had a limited path back to the core system.

Trade-off

The API was not real-time; data could lag behind the source. For this use case, bounded staleness was acceptable in exchange for clearer security, load, and recovery boundaries.
