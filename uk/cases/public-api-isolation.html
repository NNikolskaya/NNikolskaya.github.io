Як ізолювати публічне API від legacy-системи

У незалежному контракті потрібно було відкрити публічне API з останніми доступними даними legacy-платформи. Основний застосунок уже мав API з авторизацією, але змінювати його заради анонімного трафіку з інтернету означало підвищити ризик для ядра системи.

Публічний трафік ≠ навантаження на ядрочітка межа довіри та збоїв

Контекст

Новий endpoint мав бути публічним. Водночас стару систему потрібно було ізолювати від непередбачуваного зовнішнього навантаження й від збоїв на публічній межі.

Обмеження

Публічний сервіс могли перевантажити або скомпрометувати. Тому він мав бачити лише дані, призначені для публікації, без прямого доступу до основних сервісів і без секретів внутрішньої синхронізації.

Що я зробила

  1. Розділила внутрішню синхронізацію та API, доступне з інтернету.
  2. Розмістила контрольовану копію публічних даних в окремому сховищі й обслуговувала зовнішні запити лише з нього.
  3. Зробила публічний шар відтворюваним, щоб для відновлення не потрібно було ремонтувати унікальний сервер на місці.

Результат

Зовнішній трафік перестав прямо збільшувати навантаження на legacy-платформу. Між оновленнями API могло віддавати останні синхронізовані дані, а збій публічного шару мав обмежений вплив на основну систему.

Компроміс

Дані в API не були миттєво актуальними. Для цього сценарію контрольована затримка була прийнятною платою за чіткіші межі безпеки, навантаження та відновлення.
